# 実装で気をつけたいセキュリティ対策

[← ハンズオン目次](README.md)

このアプリは「ローカルで自分用に動かす」前提ですが、実装時には次の点を意識すると安全です。本番や共有環境に広げる場合は、さらに認証・認可の検討が必要です。

## 1. パス・入力の検証とインジェクション対策

| 対策 | 内容・本プロジェクトでの例 |
|------|----------------------------|
| **パストラバーサル** | ユーザーが渡すパスに `../` が含まれると、意図しないディレクトリに書き込んだり読んだりする危険がある。**対策**：`path.resolve()` で正規化したうえで、許可したベースディレクトリ（例: `expandPath(body.path)`）の「下」にあるかチェックする。`/api/open-folder` のように「任意パスを開く」API では、**サイトに紐づく path だけ許可する**など、受け入れ可能なパスをホワイトリストで限定するとよい。 |
| **コマンドインジェクション** | ユーザー入力や DB の値をそのまま `exec()` の文字列に埋め込むと、シェル経由で任意コマンドが実行される。**対策**：可能な限り `execFile(コマンド, [引数配列])` を使い、引数は配列で渡す（シェルを経由しない）。文字列でコマンドを組み立てる場合は、**シェル用のエスケープ**を行う（例: `db-sync.ts` の `shellEscape()` でシングルクォート内の `'` を `'\''` に置換）。 |
| **API の入力バリデーション** | フロントのフォームだけに頼ると、直接 API を叩かれたときに不正な値が入る。**対策**：POST body は型アサーションだけでなく、Zod などで **サーバー側でも parse/validate** する。必須項目・形式・範囲（ポート番号など）を API 内で必ずチェックする。 |

## 2. ファイルシステム・子プロセス

| 対策 | 内容・本プロジェクトでの例 |
|------|----------------------------|
| **書き込み先の限定** | サイト作成時は `path.join(basePath, body.name)` で「ベース + サイト名」だけに作成する。`body.name` に `..` や `/` が入らないよう、**名前の形式を正規表現で制限**（例: 小文字英数字とハイフンのみ）し、既存サイト名との重複もチェックしている。 |
| **削除対象パスの検証** | サイト削除で「ディレクトリも削除」するとき、**削除してよいパスか**を API で検証する。禁止例: `/`、`/usr`、`/etc`、プロジェクトルート、`data/`。ホーム以下かつ、その中に `docker-compose.yml` があるディレクトリだけを削除対象にする（`isSafeToDeleteSitePath`）。これでシステムパスや他サイト設定を誤削除しない。 |
| **exec と execFile の使い分け** | **exec** はコマンドをシェル経由で実行するため、のちにコマンド文字列に変数を足すとシェルインジェクションの危険がある。**推奨**：`docker compose` などは `execFile("docker", ["compose", "up", "-d"], { cwd: site.path })` のように **execFile + 引数配列** で実行する（シェルを経由しない）。引数に「ユーザーが変えられる値」が入る場合も execFile の配列で渡す（`open-folder` の `execFile("open", [path])` など）。 |
| **タイムアウト・バッファ** | 長時間かかるコマンド（rsync, DB 同期）には **timeout** を設定する（`db-sync.ts` の `executeRemoteCommand` など）。`maxBuffer` を大きくしすぎるとメモリを圧迫するので、必要十分な範囲にする。 |

## 3. 認証・秘密情報

| 対策 | 内容・本プロジェクトでの例 |
|------|----------------------------|
| **秘密情報の扱い** | DB パスワード・SSH 鍵パス・デプロイ先の認証情報は `data/sites.json` や `data/deploy-targets.json` に平文で入る。**対策**：これらのファイルは **Git に含めない**（`.gitignore`）。本番や共有環境では、環境変数やシークレットストアに移し、API で参照する設計を検討する。 |
| **ローカル限定の前提** | 現在は「同じマシンで Next.js を動かす人 = 全操作ができる人」という前提。ネット越しに公開する場合は、**認証（ログイン）** と **操作対象の権限チェック**（例: このユーザーはこの siteId を触ってよいか）が必須。 |

## 4. その他

| 対策 | 内容・本プロジェクトでの例 |
|------|----------------------------|
| **YAML / JSON のパース** | `templates/*.yml` や `data/*.json` を読み込むとき、**信頼できる場所のファイルだけ** を読む（`process.cwd()` 配下の固定ディレクトリ）。信頼できない入力の YAML には、意図したキー以外が含まれる可能性があるので、パース後に必要なフィールドだけを取り出す。 |
| **エラーメッセージの露出** |  API の catch で `error.message` やスタックトレースをそのまま返すと、内部パスや依存関係が漏れる。**対策**：クライアントには「起動に失敗しました」のような汎用メッセージを返し、詳細はサーバーログだけに出す。 |
| **DB ダンプの扱い** | DB 同期でエクスポートした SQL にはユーザーデータが含まれる。一時ファイル（`os.tmpdir()`）に書く場合は、処理後に **確実に削除** する。バックアップ一覧 API では、ファイル名を **ホワイトリスト**（例: 拡張子 `.sql` かつ basename が数字・ハイフンのみ）で検証し、`path.join(backupDir, filename)` で path traversal が起きないようにする。 |

## チェックリスト（実装・レビュー時）

- [ ] ユーザーが変更できる「パス」「名前」を `path.join` や `exec` に渡す前に、正規化・ホワイトリストまたは形式チェックしているか
- [ ] サイトの「ディレクトリ削除」を行う前に、削除対象パスがシステム／プロジェクト／data 等でないことを検証しているか
- [ ] シェルに渡す文字列にユーザー入力が含まれる場合、`shellEscape` 相当のエスケープをしているか（または execFile の配列で渡しているか）
- [ ] 秘密情報が入るファイルを `.gitignore` しているか
- [ ] API の POST body をサーバー側でバリデーションしているか
- [ ] 長時間・大容量のコマンドに timeout / maxBuffer を設定しているか
